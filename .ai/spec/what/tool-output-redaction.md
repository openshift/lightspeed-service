# Classic Chat Tool-Output Redaction [PLANNED: OLS-3939]

This is the **lightspeed-service** implementation contract for the shared policy in the parent `openshift/ols/.ai/spec/what/tool-output-redaction.md` ([proposed parent PR #126](https://github.com/openshift/ols/pull/126)). It is not implemented and is not a release commitment. The parent spec owns pattern categories, placeholders, defaults, conformance examples and the source-evidence boundary; do not fork that policy here. See `what/tools.md` for the existing execution, inspection and streaming contracts.

## Two policies, one optional matcher implementation

1. The service's administrator-defined `ols_config.query_filters` on prompts and attachments is unchanged. An absent or empty list means **no prompt filters**; configured filters keep their existing order and replacements. OLS-3939 introduces a **separate**, default-on `tool_output_redaction` policy for external MCP tool results. The matching implementation MAY be shared, but the tool defaults MUST NOT become prompt defaults or override user configuration.
2. Compile the effective tool-output policy once on config load/change into one matcher with named alternatives and reuse it for all tool replies. A single substitution pass over the effective result returns sanitized text, `redacted: bool`, total match count and category counts. No compile or second count scan per call. Named placeholders replace matched values while preserving surrounding structure. Do not redact standalone IP addresses or CIDRs by default. Custom patterns/removals are validated, deterministic, and handed to both runtimes by the operator; unsafe or invalid patterns fail configuration rather than silently disable protection.

## Tool execution and client boundary

3. After existing tool retries and model-facing size limits, redact both successful external results and tool-generated error text **before** calling the inspection classifier, reinjecting into the main model, wrapping with `<tool_data>`, or exposing a result to the client. Redact offloaded previews and later read/search results whenever they become model/client-visible. Inspection remains independent: enabled inspection sees sanitized input; disabled inspection does not disable redaction. A matcher failure MUST fail closed without forwarding the raw result.
4. Preserve the existing complete concurrent-round inspection gate: no `tool_result` SSE event or redaction indicator may be sent until *all* results in the round pass. On rejection, expose no passing subset, as `what/tools.md` already requires. Approval rejection messages created by the service are not external tool outputs and do not imply a redacted MCP reply. Preserve raw executor results solely for existing full-fidelity source audit obligations.
5. [PLANNED: OLS-3939] This explicitly changes the current raw `tool_result` SSE promise in `what/tools.md` rule 18n **for user-visible SSE only**. The emitted `ToolMessage.content` MUST be sanitized; its `additional_kwargs` MUST include `redacted: bool` and `redacted_count: int` for that reply, correlated by existing `tool_call_id`. A result with no replacements carries `false`, `0`. Count each source occurrence once, even when a tool's text is also projected as structured content. Raw source audit records remain full fidelity and MUST NOT be copied into the user-facing event.
6. Sanitize all other client-visible fields from the same result, including `structured_content` for MCP Apps, references that can contain tool values, replay/history/transcript representations, expansion, copy and download data. Omit a field with a safe indication rather than expose a value that cannot be sanitized. The console shows only the sanitized reply and an accessible "Sensitive values redacted" indicator when `redacted=true`, never a tooltip containing the original value. `false` means no match, **not** proof the text contains no PII; disabled protection is a separate configuration state. Non-streaming responses follow the same user-visible sanitization rule wherever they expose tool results.

## Operator handoff and telemetry

7. `lightspeed-operator` maps the default-on `OLSConfig.toolOutputRedaction` field and validated custom changes into the service's generated config and the Agentic handoff. Missing field enables the built-ins, an explicit opt-out is visible, and incompatible policies do not quietly diverge. No MCP Gateway or RHOAI dependency is required.
8. After substitution, emit one metadata-only redaction record per result with matches: bounded tool name/ID, call correlation, result/error kind, total and per-category counts. For zero matches emit no per-result redaction event. Log one payload-free state record per effective policy load/change and a warning on explicit disablement. Remove existing `ols/utils/redactor.py` debug logs of configured filter objects and post-redaction input: they can disclose secrets, including when no rule matched. On runtime failure emit one safe controlled error and fail closed; no raw payload or exception text in new diagnostics. Validate `gen_ai.tool.pii_redacted` against the adopted OTel schema before calling it standard; otherwise use a documented product-namespaced attribute. This does not redact existing source audit records.
